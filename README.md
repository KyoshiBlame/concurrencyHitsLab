# concurrencyHitsLab

`concurrencyHitsLab` — учебный проект на Go, моделирующий диспетчерскую систему обработки заявок с центральным накопителем, группами оборудования, приоритетами и ограничением параллельной работы устройств через семафор.

Проект демонстрирует работу с:

* goroutines;
* channels;
* context cancellation;
* WaitGroup;
* atomic counters;
* graceful shutdown;
* semaphore pattern;
* producer/dispatcher/worker-подходом.

## Описание задачи

Система содержит несколько групп оборудования. Каждая группа обслуживает заявки только своего номера группы.

Заявка содержит:

* уникальный ID;
* номер группы;
* приоритет от `1` до `3`.

Приоритет `3` является самым высоким, приоритет `1` — самым низким.

Пользователь при запуске программы задаёт:

* ёмкость центрального накопителя;
* количество групп оборудования `n`, где `n > 2`;
* количество устройств в каждой группе `m`, где `m > 3`.

## Как работает система

В проекте используется несколько основных компонентов:

### Generator

Генератор работает в отдельной goroutine и создаёт случайные заявки:

* случайная группа;
* случайный приоритет;
* случайная задержка между созданием заявок.

Генератор не имеет прямого доступа к накопителю. Он отправляет заявки в канал `incoming`, а дальше их принимает диспетчер.

Если центральный накопитель заполнен, диспетчер временно перестаёт читать из канала `incoming`. Из-за этого генератор блокируется на отправке и фактически “засыпает”.

### QueueDispatcher

Диспетчер является единственным компонентом, который изменяет центральный накопитель.

Он выполняет несколько задач:

* принимает заявки от генератора;
* кладёт заявки в центральный накопитель;
* принимает запросы от менеджеров групп;
* выбирает лучшую заявку для конкретной группы;
* отдаёт заявку свободному устройству;
* ведёт периодическую статистику состояния системы.

### Storage

Центральный накопитель хранит заявки в слайсе.

При выборе заявки для группы диспетчер ищет заявку с максимальным приоритетом среди заявок этой группы.

### GroupManager

Для каждой группы оборудования запускается отдельный менеджер.

Менеджер группы:

* создаёт устройства своей группы;
* запрашивает у диспетчера заявки только для своей группы;
* передаёт полученные заявки устройствам;
* использует семафор, чтобы ограничить количество одновременно работающих устройств.

### Device

Устройство — это отдельная goroutine, которая получает заявку и имитирует её обработку.

Во время работы устройство выводит в консоль:

* номер группы;
* номер устройства;
* ID заявки;
* приоритет заявки;
* оставшееся время обработки;
* количество активных устройств в группе.

### Semaphore

Семафор ограничивает число одновременно активных устройств в группе.

Лимит рассчитывается как `80%` от количества устройств в группе.

Например, если в группе `10` устройств, одновременно работать смогут только `8`.

## Запуск проекта

Склонируйте репозиторий:

```bash
git clone https://github.com/KyoshiBlame/concurrencyHitsLab.git
```

Перейдите в папку проекта:

```bash
cd concurrencyHitsLab
```

Запустите программу:

```bash
go run ./cmd
```

После запуска программа попросит ввести параметры системы:

```text
Введите ёмкость центрального накопителя:
Введите количество групп оборудования n, где n > 2:
Введите количество устройств в каждой группе m, где m > 3:
```

Пример ввода:

```text
Введите ёмкость центрального накопителя: 10
Введите количество групп оборудования n, где n > 2: 3
Введите количество устройств в каждой группе m, где m > 3: 5
```

## Корректное завершение

Программа поддерживает graceful shutdown.

Остановить систему можно двумя способами:

```text
Enter
```

или

```text
Ctrl+C
```

После этого отменяется `context`, все goroutines получают сигнал завершения, а `WaitGroup` ожидает корректной остановки всех потоков.

## Основные идеи проекта

Проект показывает, как можно построить конкурентную систему без прямого доступа всех компонентов к общему состоянию.

Главная идея:

* генератор только создаёт заявки;
* диспетчер единственный изменяет накопитель;
* менеджеры групп только запрашивают работу;
* устройства только выполняют полученные задания.

Такой подход уменьшает риск гонок данных и делает систему проще для понимания.
